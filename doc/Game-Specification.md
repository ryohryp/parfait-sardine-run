# パフェイワ（Parfait Sardine Run）ゲーム仕様書

- バージョン: 0.3
- 更新日: 2026-09-26
- 対象: 新コアループ・プロトタイプ
- ステータス: 面白さ検証フェーズ
- Tracking Issue: #68

---

## 1. 方針

本作は、従来の「60秒ランナー + 注文材料収集」を主軸とする設計から離れ、以下の体験をコアに再設計する。

> **パフェを作れ。欲張れ。そして、こぼすな。**

プレイヤーは先にパフェを作る。
その材料構成が、後半の配達アクションの難しさと報酬を直接変える。

最重要原則は次の1点。

> **作成フェーズの選択が、そのまま配達フェーズの操作感・難易度・報酬へつながること。**

---

## 2. なぜ作り直すか

従来仕様では、注文材料の判断を追加してもプレイ中の主行動は次へ収束しやすかった。

- 走る
- 障害物を避ける
- 取れる材料を拾う

演出、ランキング、コンボ、フィーバーなどを追加しても、ゲーム本体の意思決定が大きく変わりにくい。

今後は機能数ではなく、次の感情が発生するかを基準にする。

- 「もう1個積むか」
- 「ここで欲張ると危ない」
- 「この構成なら運びやすい」
- 「欲張りすぎて崩した」
- 「次はもっと上手くできる」

---

## 3. 新コアループ

1. 注文を受ける
2. 材料を選んでパフェを組み立てる
3. 材料構成から配達性能を算出する
4. 完成したパフェを配達する
5. ジャンプ、加速、着地などでパフェが揺れる
6. 一定以上の負荷で材料が落ちる
7. ゴール時の残存状態と価値から報酬を計算する
8. 次の注文へ進む

---

## 4. プレイヤーが選ぶもの

作成フェーズでは、豪華さと安全性を天秤にかける。

例:

| 材料 | 主な性質 |
| --- | --- |
| イチゴ | 価値が高いが重心が上がる |
| プリン | 重いが安定性を上げる |
| クリーム | 軽いが衝撃に弱い |
| バナナ | 速度寄りの特性を持つ |

材料ごとの数値は固定仕様ではない。
プロトタイプでは「違いが明確に体感できること」を優先する。

サーディンは特殊材料候補として残すが、最初の面白さ検証では必須にしない。

---

## 5. 配達パラメータ

完成パフェから最低限、以下を算出できる構造にする。

```ts
type ParfaitStats = {
  value: number;
  weight: number;
  stability: number;
  speedModifier: number;
  jumpModifier: number;
};
```

パラメータは作成フェーズの結果から導出し、配達中に別ルールとして上書きしない。

---

## 6. パフェの揺れと崩落

配達の面白さの中心は「操作入力がパフェに負荷を与える」こと。

最低限、次を扱う。

- ジャンプ開始
- 着地
- ダッシュ / 急加速
- 障害物との接触

負荷が安定性を超えると、上部の材料から落ちる。

プロトタイプでは高度な物理シミュレーションは不要。
プレイヤーから見て、

- なぜ揺れたか
- なぜ落ちたか
- どうすれば改善できるか

が理解できることを優先する。

---

## 7. プロトタイプ範囲

最初に作るのはフルゲームではない。

### 対象

- 1注文
- 3〜4種類の材料
- 10〜15秒程度の作成フェーズ
- 20〜30秒程度の配達フェーズ
- ジャンプ
- ダッシュ
- パフェ性能計算
- 揺れ
- 材料落下
- ゴール
- 結果表示
- モバイル 390×844 対応

### 対象外

- ガチャ
- シーズン
- 複雑なランキング
- キャラクター育成
- 大量の材料
- 経営システム
- 長いストーリー
- 複雑な物理エンジン
- 豪華な演出の作り込み
- 多数のステージ

## 8. 既存資産の扱い

可能なら以下を再利用する。

- React / TypeScript / Vite
- 現在のキャラクター表現
- ネオン系ビジュアル
- ジャンプ
- ダッシュ
- 材料データ
- 注文UI

ただし、既存コードや仕様を守るために新コアループを弱めない。

従来の注文ランナー実装は互換維持を最優先しない。
プロトタイプを独立した経路で実装してもよい。

---

## 9. UIで必ず伝える情報

配達開始時に、少なくとも次が一目で分かること。

- パフェの価値
- 重さ
- 安定性

配達中は数値を大量表示しない。

優先する情報は次。

- 今どれだけ揺れているか
- 何が落ちそうか
- どれだけ残っているか

---

## 10. スコア / 報酬

最初は単純な式でよい。

```text
最終報酬 = 完成時価値 × 配達成功率
```

配達成功率は、ゴール時に残っている材料量などから算出する。

複雑なコンボや多重倍率は、コアループの面白さが確認できるまで追加しない。

---

## 11. 成功条件

このプロトタイプは「実装できたら成功」ではない。

実プレイで以下を確認できた場合に成功とする。

1. 材料を追加するか止めるか迷う
2. 作った内容で配達の手触りが明確に変わる
3. 欲張った構成ほど高報酬だが難しい
4. 崩れた原因をプレイヤーが理解できる
5. ゴール時に「もっと欲張れた」または「欲張りすぎた」と感じる
6. 失敗後に改善案を思いつける
7. 直後にもう一度試したくなる

---

## 12. 検証方法

最低限、以下で実プレイする。

- Desktop
- Mobile viewport 390×844

1回のプレイでは判断しない。
複数のパフェ構成で配達し、操作感の差を確認する。

特に以下の3構成を比較する。

- 安全構成
- 高価だが不安定な構成
- 中間構成

差が感じられない場合は、機能追加ではなくパラメータ差またはコアループ自体を見直す。

---

## 13. 継続判断

次の開発へ進む条件は、プレイテストでコアループに手応えがあること。

手応えがない場合は、

- ランキング
- ガチャ
- 実績
- 新材料
- 新キャラ

を追加して延命しない。

先に「作る → 性能が変わる → 運ぶ → 崩れる / 届ける」が面白くなるまで直す。

---

## 14. 実装上の分離

最低限、以下を分離してテスト可能にする。

- 材料定義
- パフェ構成
- パフェ性能計算
- 揺れ / 負荷計算
- 材料落下判定
- ゴール評価
- UI表示

CanvasやReact描画へゲームルールを直接埋め込まない。
